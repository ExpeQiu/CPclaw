## 安装入口核对

下载了用户提供的 macOS/Linux 安装脚本到临时目录，未执行。常规沙箱请求发生 DNS 失败，获得单次网络执行授权后下载成功，不能据第一次错误认定官方服务不可用。

脚本实际包含：

- 按系统与架构选择二进制；默认安装位置为 `~/.local/bin`。
- 默认 Skill 根目录为 `~/.agents/skills`，安装子目录为 `dreamina-canvas-cli`。
- 支持 `DREAMINA_CANVAS_INSTALL_DIR` 和 `DREAMINA_CANVAS_SKILL_DIR` 自定义位置。
- 下载 CLI 与 Skill 包；替换前执行新二进制读取版本；Skill 更新包含锁、备份及失败恢复逻辑。
- 显式本地安装包路径包含校验和检查。不能因此宣称所有远程下载路径都做了相同的完整性验证。

Windows 安装脚本和 Linux 实机安装未验证。当前不需要重装现有 CLI，也没有证明在线安装版本与本机版本完全一致。

## 命令能力映射

以下基于本机 schema 和帮助，不代表远端调用成功：

| 产品需求 | 已声明能力 | 接入处理 |
|---|---|---|
| 发起登录 | `auth login` | 返回 challenge，向用户展示官方授权地址和验证码 |
| 等待授权 | `auth wait --device-code …` | 使用原 challenge 等待，不反复发起登录 |
| 检查身份 | `auth status` / `auth account` | status 用于本地状态；account 与远端可用性仍待实测 |
| 打开指定画布 | `canvas ls` | 帮助明确返回 projectId/name/webUrl；后续使用实际返回地址 |
| 查询内容 | `node find` / `node show` | 执行修改前读取目标，不能假设获得原生页选区 |
| 编辑和生成 | `node create` / `node edit` / `node run` | 区分保存与运行，使用 schema 真实参数 |
| 费用处理 | `node quote` / `node confirm` | 先报价，按服务端协议取得用户批准 |
| 恢复查询 | `operation status` / `operation wait` | 使用原操作引用；必要时显式 projectId |
| 产物交付 | `resource get` / `resource download` | 查询终态并验证产物可读取，尚未真实测试 |
| 取消生成 | 当前 schema/帮助未声明取消命令 | 首期只提供停止等待；提示远端可能仍在运行 |

登录响应契约包含 `challenge.deviceCode`、`userCode`、`verificationUri`、可选 `verificationUriComplete` 以及轮询间隔和有效期。设备授权引用仅在授权流程中使用，不进入普通诊断记录。

## 页面容器实测

用项目安装的 Electron 启动临时验证程序，创建隐藏 BrowserWindow，将 WebContentsView 加入 contentView 并设置为右侧区域。验证脚本不导入 CPclaw 主进程，不加载用户既有浏览器 profile。

配置：`sandbox=true`、`nodeIntegration=false`、`contextIsolation=true`，使用独立非持久 partition，无 preload，拒绝弹出窗口；临时 userData 位于 `/tmp/cpclaw-embed-probe/profile`。

实测输出：

```json
{"loaded":true,"electron":"33.4.11","title":"即梦AI - 即刻造梦","url":"https://jimeng.jianying.com/","scope":"public-homepage-only"}
```

该结果证明公开首页能在 WebContentsView 中完成加载。验证窗口隐藏，未执行视觉检查，因此不宣称布局、输入交互或画布可用。运行中出现缓存和媒体解码诊断信息，虽未阻断页面加载，仍需在可见原型中检查媒体显示。

首次临时脚本误从 npm 包路径导入 Electron，得到二进制路径字符串而非运行时 API；改为运行时 `require('electron')` 后重新验证通过。该错误未涉及项目代码。

容器建议是技术候选，不是已完成的实现。Electron 官方说明可用 iframe、WebContentsView 等方式嵌入网页；iframe 受页面 CSP 限制，官方当前不推荐优先使用 webview 标签。参考：[Web Embeds](https://www.electronjs.org/docs/latest/tutorial/web-embeds)、[webview](https://www.electronjs.org/docs/latest/api/webview-tag)、[Security](https://www.electronjs.org/docs/latest/tutorial/security)。最新文档仅作为方向参考，当前版本可用性由本次 33.4.11 实测提供有限证据。

## 登录与远端读取复查（同日补充）

用户明确同意启动登录授权后，执行 `auth login`。普通沙箱发生 DNS 错误，获准网络执行后返回 `status=reused`、`loggedIn=true`，没有创建新的授权 challenge。随后 `auth status` 同样返回已登录。这修正了前述“当前未登录”的即时状态；前面的结果保留为第一次检查记录。

但实际执行 `canvas ls --limit 5` 失败：退出码 11，`class=auth_required`、`reason=oauth_scope_insufficient`、`retryable=false`。服务端明确要求更新 CLI 与 Skill，并以同一 profile 执行 `auth login --force` 重新授权。关联请求 ID：`20261024134924CBF7A2A5A7F34B01C7C9`。

因此当前状态应显示「登录权限不足，需要更新并重新授权」，而不是「就绪」。`auth status` 的本地 loggedIn 字段不能单独作为应用可用性的验收依据，必须补充一次获准的实际只读请求。

截至本记录，未升级安装、未使用 force 清除授权、未取得画布列表或真实画布 URL。下一步需用户同意更新既有 CLI 与 Skill，再按实际新版本能力重新启动授权；不以反复重试画布列表解决权限问题。
