# 请求上下文预算与文档续接

日期：2026-11-06。问题来自e73bab91和2ece49ae两次长会话：平台256KiB请求体限制先于模型token容量触发，超限销毁socket，桌面误报模型连接失败；分段文档停在已保存草稿。

## 方案与验收

1. **分开计算预算。** HTTP预算使用UTF-8 JSON字节数；模型容量与压缩使用tokens；输出长度、消息数与模型调用次数保持独立。本轮不修改模型声明容量、压缩阈值、输出预算或调用次数。
2. **一份传输配置。** contracts导出DEFAULT_HARNESS_BODY_BYTES及resolveHarnessBodyLimit，平台与桌面Harness代理共用。默认8MiB，启动时读取CPCLAW_HARNESS_MAX_BODY_BYTES，允许256KiB—32MiB的整数字节值，错误配置拒绝启动。平台listenPlatform的harnessMaxBodyBytes仅供宿主/测试明确覆盖。其他API原来的体积限制不随之提高。
3. **拒绝必须可解释。** 平台超限清空缓冲并停止收集后续块，保留HTTP响应通道，返回413 / REQUEST_BODY_TOO_LARGE，记录已接收至少多少字节及限制值。后续块被消费但不留存，不保存正文或凭据。非法JSON仍沿用原解析错误。413不进入模型、不占用推理额度，不自动重试。
4. **代理与诊断贯通。** 本机原约2MB上限同步统一预算。模型上下文先拼接Buffer再解码UTF-8，防止中文在网络块边界损坏。每次远端请求记录实际转发字节数；413传播明确错误代码、阶段、上限，桌面展示“请求上下文超过传输上限”，不冒充模型断连。
5. **草稿原位续接。** 不改动现有delivery原子发布机制：part=0,complete=false只是草稿；当前会话可read_resource(kind=draft)读取已提交段数与原文，使用同一documentKey从下一段提交，complete=true时发布一次。禁止为了恢复整轮重放或用宿主猜写缺失正文。本轮用受控测试验证一次失败后续接的逐字一致性，不改写用户实际草稿。

## 为什么采用8MiB

256KiB是传输保护值，不是模型容量。用户已确认的正常任务仅约6.9万输入tokens即被该传输保护值截断；提高传输预算让模型自己的上下文治理先发挥作用。8MiB给JSON结构、工具schema和中英文编码留出空间，同时保持有界。它不是新的模型token额度，也不保证任意大小会话都能处理。前置代理、上传超时、消息条数、供应商上下文限制仍独立生效。

## 上下文增长治理

继续使用Harness自身的token计量与压缩，不在宿主截断或摘要历史。原始回执仍持久化；大结果通过read_tool_result分页，模型可按需读取。8MiB不能替代token压缩；自动压缩也不能替代明确的HTTP错误返回。

本轮不创建新的诊断Agent、不重建第二份会话记忆、不提供付费生成自动重提。普通自然语言“存档以上内容”仍由内核理解并提交文档；文档是否完成以complete及发布回执为准。

## 发布与回滚

先发布平台，再更新桌面。仅更新桌面仍会遇到旧平台256KiB限制；旧平台销毁socket的行为也无法仅靠桌面可靠识别。默认提高上限不需要迁移数据库，预算可配置回调，但不应恢复销毁socket。生产发布、安装版、真实模型质量须单独验收。

## 验收标准

- 超过旧256KiB限制的中文请求逐字到达受控上游，返回成功。
- 超限分块上传返回可解析413，模型调用计数为0，同一平台随后可正常处理请求。
- 代理跨UTF-8字节边界传输不损坏中文，保存实际请求体字节数。
- 413错误保留阶段及预算，界面错误类别不是MODEL_CONNECTION_FAILED。
- 第一段保存后中断，新输入在同会话补齐后续段落；全文逐字一致，仅发布一份。
- 构建、针对性测试、仓库完整验证通过；未执行项目不记为通过。
