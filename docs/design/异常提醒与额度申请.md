# 异常提醒与额度申请

目标：用户能快速理解原因、影响、保留进度与下一步，并直接完成处理。异常提示不以状态码代替解释，也不把“检查完成”或“已受理”当作任务完成。

## 已实现的提醒层级

| 场景 | 提醒方式 | 主要说明 | 直接动作 |
|---|---|---|---|
| 模型tokens额度耗尽 | 自动弹窗＋聊天内保留入口 | 模型额度与即梦积分分别计算；本轮暂停，请求/回执保留 | 申请新增额度 |
| 官方授权不足 / 平台登录失效 | 自动弹窗 | 缺少哪类授权、当前任务已暂停 | 自诊断重新授权 / 前往登录 |
| 并发已满、临时429、502或超时 | 聊天内明确提示与动作入口 | 说明暂时受阻，未知原因保持未知，不把所有429都称为余额不足 | 核实占用/额度；安全时继续原请求 |
| 图片读取或预览失败 | 聊天内提示 | 先核实已有文件，不在没有文件证据时声称“原图已保存” | 查找并恢复图片 |
| 图片交付已恢复 | 更新原有提醒 | 明确恢复了图片交付，保留原始错误；不宣称其他目标全部完成 | 查看恢复报告与成果 |
| 项目检索无匹配 | 原有轻提示 | 未引用项目片段，不当作任务故障 | 用户按需补材料 |

所有异常统一采用：**短标题 → 原因 → 当前影响 → 已保留内容 → 一个主要动作**。原始状态码和错误留在折叠的技术详情中。自动弹窗按账号、对话、消息与错误类型去重；用户可稍后处理，聊天中的入口仍保留。

## 模型额度不足弹窗

标题：「模型额度不足，任务已暂停」

说明：「平台模型可用额度已用完，暂时无法继续思考和执行。」

影响：「申请新额度后可继续当前任务。即梦积分与模型tokens额度分别计算。」

保留进度按真实回执区分：没有工具记录时说明请求已保留；仅有只读查询时说明这轮尚无生成/写入提交；已有写入或生成记录时说明将先核实原任务，避免重复生成。

显示当前可用tokens、额度上限与下一次调用所需最低预留。用户填写申请新增量，默认100万tokens，每次支持1至100万的整数。当前额度申请采用**自动审批**：提交后由服务端鉴权、审批、增加当前账号额度、回读结果，并记录审计。

审批到账后显示「新额度已到账」、实际可用tokens与「已自动批准」状态。此前没有外部副作用时可点击「继续原任务」；已有外部执行时改为「检查并恢复原任务」。申请额度本身不重复执行原任务，不清零历史用量，不改变并发限制，不改动即梦积分，也不替其他账号申请。

如果响应丢失，提示「申请结果暂未确认」，按钮改为「核实原申请结果」。核实时复用按当前账号/对话保存在本机的原申请编号，服务端不重复增加额度；未确认到账前不显示成功。申请已批准但可用额度仍低于最低预留时继续说明不足，不误报任务已经可恢复。

## 防止再发

- 开始模型任务前核实额度，已知可用额度低于最低预留时停止新模型调用和工具准备；诊断同时检查额度/并发，低于10%在诊断报告预警。
- Harness保留平台明确返回的额度/并发原因，不再把所有信息压成一个429。
- 服务回执区分已证明的只读查询与生成/写入；只读准备允许安全续接，已有外部操作仍禁止整轮重放。原回执按步骤追加保留。
- 诊断台账沉淀额度耗尽、并发限制与429处理规则，区分已观察问题与已验证修复。
- 额度申请用服务端持久化幂等记录与事务，账号/企业权限由平台凭据确定，客户端不能指定其他员工。

## 实现与兼容性

平台新增 `POST /v1/me/quota-requests`（`requestId`、`additionalTokens`），批准结果含 `status=approved`、`approvalMode=auto`、当前quota与是否重放。`GET /v1/me/quota` 声明自动审批能力和单次申请上限。申请记录位于平台 `quota_requests`，审批写入审计日志。

桌面端新增 `account.quota` / `account.quotaRequest` 工作进程接口，消息保存结构化issue。统一文案位于 `apps/desktop/task-issue.mjs`，弹窗位于 `renderer/task-issues.js`。

旧平台未声明申请能力时，弹窗明确提示更新平台服务或重新检查，不伪装成申请成功。此功能需要**平台与桌面端同时发布**；本次开发验证没有修改生产额度或调用付费模型。
