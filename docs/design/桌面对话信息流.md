## 一次发送

1. 界面提交 `chatId`、`requestId` 和文本；编辑文档时还包含目标文档及预期哈希。
2. preload 通过 IPC 将命令交给主进程。主进程读取当前账号，工作区客户端再用带请求编号的 JSON 行发送到独立 Node 子进程。
3. `chat-service` 校验账号、聊天归属、重复请求及活动槽，先保存用户消息和 streaming 回复占位，再准备上下文。
4. 上下文包括当前问题和最近成功问答对，常规上限为 31 条、32000 字符。取消、失败的回复不作为成功上下文。安装版 0.0.5 可将所选技能/专家组合的方法加入上下文；文档修改请求可加入原文和修改要求。
5. 工作进程先调用 `/v1/session/refresh`，更新本机刷新令牌，随后用访问令牌调用 `/v1/chat/stream`。界面不直接访问供应商。
6. 平台做鉴权、请求重放及额度控制，通过服务端模型网关请求 MiniMax-M3。模型 SSE 正文片段转成 NDJSON 返回工作进程。
7. 工作进程将正文节流保存（约 200ms），并经 stdout 的 `{event}` 传给主进程。主进程只转发当前账号的 `chat.event`，界面按聊天与请求编号更新消息。整个 IPC invoke 的最终结果在该轮结束后另行返回，流事件不必等待 invoke 完成。
8. 完整结束后保存 done 终态；安装版的文档计划分支才创建实际 `.md` 文件及版本记录，并在 finish 事件中交付成果卡片。文档失败时保留回复正文并显示保存错误。

## 取消与故障

`停止生成 → chat.cancel → 同一 IPC/子进程通道 → AbortController → HTTP 断连 → 平台取消供应商请求`。已收到的正文保留为 cancelled；流截断、超时或错误不能标成成功。工作进程再次启动时将 streaming 消息标记为 interrupted，用户可重试。平台释放并发位，未知用量保持 unknown。

## 需要区分

- 普通聊天直接走平台聊天网关，本链路没有经过 Harness，也没有让模型直接执行本机 shell。
- 安装版 0.0.5 的文档产出依靠本机文档计划和完整回复保存。
- 工作区 0.0.6 新增 `documentTools`、`activity` / `document` 事件和 `deliver_document` 校验，不应当成安装版已发送的协议。
- 本图仅解释当前对话链路，不代表重新完成部署或全量功能验收。

主要实现位置：`apps/desktop/{preload.cjs,main.mjs,workspace-client.mjs,workspace-worker.mjs,chat-service.mjs,document-service.mjs,renderer/chat.js}`，平台接口在 `packages/platform/src/http.ts`，模型流解析在 `packages/model-gateway/src/chat-stream.ts`。安装版差异从应用包内对应文件直接读取核对。
